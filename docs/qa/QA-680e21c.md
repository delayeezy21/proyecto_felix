## Horario inmutable y `felix.time_travel`: ¿se puede explotar?
La regla es `session_user = 'postgres'` **y** `felix.time_travel = 'on'`.

| Vía | Resultado | Evidencia |
|---|---|---|
| PostgREST (dueño, vet o admin) | No | sin grant de UPDATE sobre `visits` (403). `set_config` no está expuesto en la API (`/rpc/set_config` → 404). PostgREST no traslada headers a GUC arbitrarios, solo a `request.*` |
| Clave de servicio por REST | No | PATCH de `scheduled_at` y de `status` → 403/4xx (el guardián rechaza aunque `service_role` tenga grants) |
| Sesión como PostgREST (`set session authorization authenticator; set role service_role`) con `felix.time_travel` y `felix.visit_transition` fijados a mano | No | "El horario de una visita no se modifica". El cambio de estado con la marca fijada a mano también falla ("permission denied for function visit_edge_allowed"); es un bloqueo incidental, pero vale |
| Funciones SECURITY DEFINER llamadas desde la API | No | cambian `current_user` a `postgres`, pero `session_user` sigue siendo `authenticator`. Usar `session_user` y no `current_user` es lo correcto. Ninguna función de la app fija `felix.time_travel` (`grep set_config`: solo `felix.visit_transition` y `request.jwt`) |
| Sesiones con `session_user = postgres` | Sí, a propósito | conexión directa con la contraseña del dueño de la BD (pgTAP, E2E, editor SQL del dashboard). Los jobs de pg_cron también corren como `postgres`, pero sus comandos son fijos y no fijan la marca. Riesgo aceptable: quien tiene esa sesión ya es administrador de la base |

**Conclusión:** la excepción no se puede explotar desde la app ni desde la clave de servicio.
